# ADR-001: Выбор архитектуры сервиса Notes Service

## Статус

Принято.

## Дата

22.09.2026

## Контекст

Notes Service представляет собой клиент-серверную систему для создания,
хранения, редактирования и синхронизации пользовательских заметок.

Необходимо спроектировать архитектуру, которая обеспечивает:

- централизованное хранение пользовательских данных;
- доступ к заметкам с нескольких устройств;
- синхронизацию изменений;
- контроль конкурентного редактирования;
- аутентификацию пользователей;
- чёткий контракт взаимодействия клиента и сервера;
- возможность дальнейшего развития системы.

Особое внимание уделяется проблемам, выявленным при архитектурном анализе
существующих приложений для работы с заметками: потеря данных, задержки
синхронизации, конфликты изменений и недостаточная изоляция компонентов.

## Рассмотренные варианты

### Вариант 1. Монолитная архитектура

Все серверные функции реализуются в одном приложении и используют единую
базу данных.

Преимущества:

- простота разработки;
- простой процесс развёртывания;
- минимальные накладные расходы на взаимодействие компонентов.

Недостатки:

- высокая вероятность роста связанности компонентов;
- усложнение сопровождения при развитии системы;
- ограниченная независимость отдельных функциональных частей.

### Вариант 2. Микросервисная архитектура

Аутентификация, работа с заметками, синхронизация и другие функции
реализуются отдельными сервисами.

Преимущества:

- независимое масштабирование компонентов;
- хорошая изоляция функциональных областей;
- независимое развёртывание сервисов.

Недостатки:

- высокая сложность инфраструктуры;
- необходимость организации межсервисного взаимодействия;
- дополнительные проблемы согласованности данных;
- избыточность для системы рассматриваемого масштаба.

### Вариант 3. Модульный монолит

Система развёртывается как единое серверное приложение, однако внутри
разделяется на независимые функциональные модули с явно определёнными
границами ответственности.

Основные модули:

- Authentication;
- Notes;
- Synchronization;
- Attachments.

## Решение

Для Notes Service выбрана архитектура модульного монолита.

Данный вариант позволяет сохранить простоту разработки и развёртывания
монолитного приложения, одновременно обеспечивая логическое разделение
ответственности между компонентами.

Клиентские приложения взаимодействуют с сервером через REST API.
Контракт API формализуется с использованием спецификации OpenAPI.

Для хранения основных данных используется реляционная СУБД PostgreSQL.

Для доступа к защищённым ресурсам применяется аутентификация на основе
JWT Bearer Token.

## Архитектурные решения

### REST API

Взаимодействие клиентских приложений с сервером выполняется через REST API.

Использование REST обеспечивает единый интерфейс для различных клиентов
и позволяет формализовать контракт взаимодействия средствами OpenAPI.

### PostgreSQL

Основным постоянным хранилищем системы является PostgreSQL.

Реляционная модель подходит для хранения пользователей, заметок,
тегов, устройств, вложений и информации о синхронизации.

### JWT-аутентификация

После успешной аутентификации пользователь получает JWT-токен.

При обращении к защищённым endpoint токен передаётся в заголовке:

Authorization: Bearer <token>

### Версионирование заметок

Каждая заметка содержит номер версии.

При изменении заметки клиент передаёт известную ему версию объекта.
Это позволяет серверу обнаружить ситуацию, когда заметка была изменена
другим клиентом после последней синхронизации.

При обнаружении несовместимых изменений сервер возвращает информацию
о конфликте вместо неявной перезаписи данных.

### Синхронизация

Клиент может запрашивать изменения, произошедшие после последней
успешной синхронизации.

Такой подход уменьшает объём передаваемых данных и позволяет клиентам
поддерживать актуальное состояние заметок без постоянной полной загрузки
всего набора данных.

## Последствия принятого решения

### Положительные последствия

- единый формализованный контракт между клиентом и сервером;
- логическое разделение компонентов;
- относительно простое развёртывание;
- возможность обнаружения конфликтов изменений;
- возможность дальнейшего выделения отдельных модулей в сервисы;
- централизованный контроль доступа к пользовательским данным.

### Отрицательные последствия

- приложение остаётся единицей развёртывания;
- ошибка серверного приложения потенциально влияет на несколько модулей;
- масштабирование отдельных модулей независимо друг от друга ограничено;
- механизм синхронизации увеличивает сложность серверной логики.

## Риски

Основными архитектурными рисками являются:

1. возникновение конфликтов при одновременном редактировании заметки;
2. рост нагрузки при увеличении количества пользователей и заметок;
3. увеличение связанности модулей по мере развития проекта;
4. усложнение механизма синхронизации;
5. необходимость обеспечения обратной совместимости API.

Для снижения данных рисков используются явные границы модулей,
версионирование данных и формализованный API-контракт.
