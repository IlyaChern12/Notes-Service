# ADR-003: Управление конкурентным доступом

## Статус

Принято.

## Дата

22.10.2026

## Контекст

Одни и те же данные одновременно изменяют несколько устройств и вкладок пользователя, повторы запросов после таймаута и несколько копий серверного приложения. Дефекты R6 и R7 из [анализа отзывов](../analysis/user-reviews-analysis.md) – именно потерянные обновления. Блокировки в памяти процесса не работают при горизонтальном масштабировании.

## Решение

1. Уровень изоляции – READ COMMITTED. SERIALIZABLE не используется: для каждой точки гонки выбирается явный механизм по правилу «частота конфликтов × цена ошибки».
2. Правка и удаление заметки – оптимистическая блокировка: условие `version = expectedVersion` входит в саму команду `UPDATE`; при несовпадении – `409 VERSION_CONFLICT` с текущей версией. Автоматический повтор конфликтующей правки запрещён.
3. Ротация токена обновления – `SELECT … FOR UPDATE` в короткой транзакции (ADR-004).
4. Повторы изменяющих команд – заголовок `Idempotency-Key` и таблица `idempotency_keys` с `PRIMARY KEY (user_id, key)`; ключ, эффект и ответ фиксируются одной транзакцией; другое тело с тем же ключом – 422; срок хранения 24 часа.
5. Изменение агрегата и запись события фиксируются одной транзакцией (транзакционный outbox); обработчики outbox выбирают записи через `FOR UPDATE SKIP LOCKED`; получатели дедуплицируют события по `eventId` (`processed_events`).
6. Короткие транзакции без сетевых вызовов, единый порядок блокировки строк, `lock_timeout` и `statement_timeout`.

Подробный разбор с SQL – [race-conditions.md](../concurrency/race-conditions.md).

## Последствия

Положительные:

- конфликт правок обнаруживается вместо незаметной потери данных;
- гарантии одинаковы для любого числа серверных копий;
- повтор запроса безопасен для клиента.

Отрицательные:

- клиент обязан хранить версию и ключ операции и показывать конфликт пользователю;
- таблицы `idempotency_keys` и `outbox` требуют фоновой очистки;
- обработчик ленты синхронизации – потенциальное узкое место, требует наблюдения.
